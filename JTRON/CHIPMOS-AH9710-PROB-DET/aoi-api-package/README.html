AH9710 AOI-API — 開發者 Package

小型 FastAPI 服務，用來判定探針針尖是否已經與 probe card 接觸（ROI 影像為對焦狀態 = contact，失焦 = non_contact）。本服務對所有 probe card 類型通用——單一 calibration、單一 fixed reference ROI。

v7.4 · 服務 port 8000（可透過 config/aoi_api.json 調整） · 模型：以 5 個影像特徵為輸入的 logistic regression · 判定門檻 probability_contact ≥ 0.5 · 建議相機解析度 1540 × 1050 · v7.4 起 non_contact 不存檔

1. Package 內容 2. 安裝與啟動 3. 整體資料流 4. 設定檔 5. Log 紀錄 6. HTTP endpoints 7. 批次掃描工具 8. 給 monitor 的呼叫方式 9. 特徵說明 10. 重新校正 11. 待確認事項 12. 疑難排解

1. 這個 Package 的內容

aoi-api-package/
├── prob_api.py            # FastAPI 服務本體 (v7.4)
├── config/
│   └── aoi_api.json       # 所有可調整的路徑與 server/log 設定（見 §4）
├── local_output/
│   ├── calibration.json   # 訓練好的模型（通用、單一物件，無 per-category 鍵）
│   ├── contact/           # 判定為 contact 時的 JPG 儲存位置（原圖 + 裁切兩個檔）
│   └── non-contact/       # （保留但 v7.4 起不寫入；見 §3、§8）
├── logs/
│   └── aoi_api.log        # 每次 predict 的 JSON Lines 紀錄（見 §5；每日午夜輪替）
├── requirements.txt       # Python 相依套件
├── scan_batch.py          # CLI 工具——批次掃描資料夾、印出每張的 KPI 與判定
├── samples/
│   ├── contact.png            # 完整 1540×1050 RCM 截圖（contact）
│   └── non_contact.png        # 完整 1540×1050 RCM 截圖（non_contact）
├── README.md              # markdown 版
└── README.html            # 本文件（離線可讀，不需後端）
重要：請從 package 的根目錄啟動服務，才能讓 ./config/aoi_api.json、./local_output/calibration.json、./logs/ 等相對路徑解析正確——程式啟動時會從當下目錄讀取。

2. 安裝與啟動

# 建立 Python 3.10+ 環境（venv / conda 皆可）
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# 啟動服務（會讀取 config/aoi_api.json）
python prob_api.py
# 或指定自訂設定檔：
AOI_API_CONFIG=/etc/aoi/aoi_api.json python prob_api.py
# 或直接用 uvicorn（仍會載入預設設定）：
uvicorn prob_api:app --host 0.0.0.0 --port 8000

當 GET http://localhost:8000/api/v1/health 回傳 {"status":"ok", "calibrated": true, ...} 就表示啟動成功。Swagger UI 位址：http://localhost:8000/docs。

3. 整體資料流

RCM 相機 (1540 × 1050)
   │ snapshot
   ▼
contact-monitor-service  ← 您同事的程式
   │ 不裁切、不 resize，直接上傳 1540×1050 整張
   ▼
POST /api/v1/predict  multipart file=<整張 1540×1050>
   │
   ▼
AOI API (prob_api.py)
   │ 1. 讀入 → 依 reference_roi 裁出 385×420 crop
   │ 2. 計算 5 個特徵 → logistic → status
   │ 3. 只在 contact 時存 2 個 JPG 到 ./local_output/contact/：
   │       <timestamp>.jpg          ← 原圖 1540×1050 + 藍色 ROI 外框 (給人工檢視)
   │       cropped_<timestamp>.jpg  ← 原始 385×420 crop (給模型除錯)
   │    non_contact 不存檔，response 的 roi_image / fullframe_image 回 null
   │ 4. 寫一行 JSON Lines 到 ./logs/aoi_api.log（詳見 §5；null 路徑也會如實記錄）
   │ 5. 回傳 JSON（status、roi_image、fullframe_image、features、probability）
   ▼
monitor 依 response 更新 Redis / LED、Web UI 依 `roi_image` 顯示（null 時不顯示）

Monitor 端的工作因此簡化：只負責 fetch snapshot → 上傳，裁切、存檔、日誌都由 AOI 做。

4. 設定檔 config/aoi_api.json

所有可調整的路徑與 server/logging 設定都寫在這裡；程式啟動時讀取，不存在時使用內建預設值。檔案回收 service 可讀取同一份設定來得知要掃哪些資料夾（見 §8「儲存量估算」）。

預設內容：

{
  "server": {
    "host": "0.0.0.0",
    "port": 8000
  },
  "paths": {
    "calibration_json": "./local_output/calibration.json",
    "contact_dir": "./local_output/contact",
    "non_contact_dir": "./local_output/non-contact",
    "log_dir": "./logs"
  },
  "logging": {
    "level": "INFO",
    "filename": "aoi_api.log",
    "rotation": "daily",
    "backup_count": 7
  }
}

各欄位：

欄位說明
server.host, server.portuvicorn 綁定位址與 port
paths.calibration_json模型 calibration 檔路徑（相對或絕對皆可）
paths.contact_dirpredict 判定為 contact 時 JPG 寫入的資料夾
paths.non_contact_dirpredict 判定為 non_contact 時 JPG 寫入的資料夾
paths.log_dirJSON Lines log 檔寫入的資料夾
logging.levelPython logging level（DEBUG / INFO / WARNING / ERROR）
logging.filename當日 log 檔名（固定；輪替後會變成 aoi_api.log.YYYY-MM-DD）
logging.rotation目前僅支援 daily（午夜輪替）；留此欄位以便未來擴充
logging.backup_count保留幾份輪替過的舊檔（超過的最舊檔會被 handler 自動刪除）

換到不同的路徑或 port：直接改 config/aoi_api.json，然後重啟服務。StaticFiles 對外的 URL path 固定為 /local_output/contact/... 與 /local_output/non-contact/...，不受 paths.contact_dir / paths.non_contact_dir 影響，所以 monitor 端的呼叫合約穩定。

換到完全不同位置的設定檔：在啟動前設定環境變數 AOI_API_CONFIG 指向目標檔案即可，例如 AOI_API_CONFIG=/etc/aoi/aoi_api.json python prob_api.py。

5. Log 紀錄（JSON Lines）

每次 POST /api/v1/predict 完成後，AOI 會把完整 response + 來源檔名 + 處理耗時寫入 <log_dir>/aoi_api.log，格式為 JSON Lines（每一行是一個獨立 JSON 物件，方便 jq、pandas、grep 處理）。另會紀錄 startup、shutdown、predict_error 事件。

檔名輪替：使用 Python TimedRotatingFileHandler，每日 00:00 午夜產生新檔，舊檔改名成 aoi_api.log.YYYY-MM-DD。保留天數由 logging.backup_count 控制（預設 7）；超過的最舊檔自動刪除。

Predict 事件格式範例（單行，為了易讀以下有換行）：

{
  "ts": "2026-11-10T11:41:52.156",
  "level": "INFO",
  "event": "predict",
  "filename": "Screenshot 2026-11-06 121216.png",
  "status": "contact",
  "roi_image": "/local_output/contact/cropped_20261110_114152_156.jpg",
  "fullframe_image": "/local_output/contact/20261110_114152_156.jpg",
  "laplacian_score": 24.25,
  "probability_contact": 0.8824,
  "features": {
    "lap_var": 24.2527, "mean": 55.1213, "std": 23.2327,
    "edge_den": 0.0128, "grad_mag": 40.9087
  },
  "latency_ms": 23.5
}

其他事件：

event欄位時機
startupversion, config_path, paths服務啟動時
shutdownversion服務停止時
predict_errorfilename, error上傳的影像無法解碼、為空、或 ROI 無效

查詢範例：

# 查看今日所有 contact 判定
grep '"status": "contact"' logs/aoi_api.log | wc -l

# 用 jq 挑出所有 latency > 100ms 的紀錄
jq -c 'select(.event == "predict" and .latency_ms > 100)' logs/aoi_api.log

# pandas 快速匯入
python -c "import pandas as pd; df = pd.read_json('logs/aoi_api.log', lines=True); print(df.describe())"

6. HTTP endpoints

GET /api/v1/health — 可用性檢查

contact-monitor-service 在 STARTING 狀態會用這個 endpoint 確認 AOI 已經準備好。

{
  "status": "ok",
  "service": "aoi-api",
  "version": "7.4",
  "calibrated": true
}

GET /api/v1/config — 模型 metadata

Monitor 啟動時呼叫一次即可；用 reference_roi 確認 RCM framing 與訓練幾何一致。

{
  "reference_roi": { "rx1": 0.25, "ry1": 0.45, "rx2": 0.5, "ry2": 0.85 },
  "model": "logistic",
  "features": ["lap_var", "mean", "std", "edge_den", "grad_mag"],
  "decision_threshold": 0.5,
  "trained_on": { "n_contact": 10, "n_non_contact": 14 }
}

POST /api/v1/predict — 判定一張 RCM 截圖

multipart/form-data，單一欄位 file。上傳 完整 RCM 截圖（建議 1540 × 1050），AOI 會自行裁切。

curl -s -X POST http://localhost:8000/api/v1/predict \
  -F 'file=@samples/contact.png' | jq .

Response：

{
  "status": "contact",
  "roi_image": "/local_output/contact/cropped_20261107_123451_018.jpg",
  "fullframe_image": "/local_output/contact/20261107_123451_018.jpg",
  "laplacian_score": 24.74,
  "probability_contact": 0.9138,
  "features": {
    "lap_var": 24.74,
    "mean": 55.11,
    "std": 23.31,
    "edge_den": 0.015,
    "grad_mag": 41.35
  }
}
欄位說明
statuscontact 或 non_contact——monitor 需要的二元判定
roi_imagecontact 時為裁切後 ROI 影像 URL path（/local_output/contact/cropped_<timestamp>.jpg）；non_contact 時為 null（v7.4 起不存檔）
fullframe_imagecontact 時為原圖 URL path（/local_output/contact/<timestamp>.jpg，含藍色 ROI 外框）；non_contact 時為 null
laplacian_score等同於 features.lap_var——保留以符合設計文件相容欄位
probability_contactlogistic 模型輸出的 0.0 – 1.0 機率
features五個特徵的全部數值（詳見 §9）

non_contact response 範例（note the null paths）：

{
  "status": "non_contact",
  "roi_image": null,
  "fullframe_image": null,
  "laplacian_score": 11.68,
  "probability_contact": 0.0016,
  "features": { "lap_var": 11.6823, "mean": 48.4003, "std": 14.0118, "edge_den": 0.0048, "grad_mag": 7.402 }
}

GET /local_output/contact/<file>.jpg — 取回已儲存的 JPG

以 FastAPI StaticFiles 提供；roi_image 與 fullframe_image 回傳的路徑可直接拼接服務 base URL，例如：
http://192.168.137.101:8000/local_output/contact/20261107_123451_018.jpg

local_output/calibration.json 不會被對外提供，因為我們只掛載 contact/ 與 non-contact/ 兩個子目錄。

掃描資料夾裡的所有影像，逐張呼叫 API，印出每一張的 KPI 與判定、最後顯示 summary。本工具不做任何裁切——API 內部完全處理。

python scan_batch.py samples/

7b. 有 label 時量測準確率

把資料放到 <root>/contact/ 和 <root>/non-contact/ 子目錄，然後加 --labeled：

python scan_batch.py labeled_data/ --labeled

輸出會多一個 truth 欄位，summary 也會附上 accuracy。

7c. 輸出成 CSV

python scan_batch.py samples/ --csv results.csv

CSV 會包含兩個已儲存檔案的 URL path（roi_image 與 fullframe_image）。

7d. 指定不同的 API 位址

python scan_batch.py samples/ --url http://192.168.137.101:8000

所有參數

positional:
  path                 要掃描的影像資料夾

options:
  --url URL            AOI API base URL（預設 http://localhost:8000）
  --timeout SECONDS    HTTP timeout（預設 5.0 秒）
  --csv PATH           將每張結果寫入指定 CSV 檔
  --labeled            把 <path> 當作含 ./contact/ 和 ./non-contact/ 的 root

8. contact-monitor-service 應該怎麼呼叫這個 API

Monitor 端的工作非常單純：不要裁切、不要 resize，直接把 RCM 整張 snapshot 以 file 欄位 POST 給 /api/v1/predict。

相機設定（必須）

  • RCM 全畫面解析度：1540 × 1050 px
  • 構圖：確保訓練時的 ROI 區域（左 25%–50% 寬 × 上 45%–85% 高）框到探針與 die 的接觸區

這組設定讓 AOI 內部裁切後得到 385 × 420 原生 crop，與訓練資料幾何一致，不需要在 monitor 或 AOI 任一端做 resize。

範例呼叫（Python）

import requests

with open(rcm_snapshot_bytes, "rb") as fh:
    r = requests.post(
        "http://192.168.137.101:8000/api/v1/predict",
        files={"file": ("snap.jpg", fh, "image/jpeg")},
        timeout=3,
    )
resp = r.json()
# resp["status"]              → "contact" or "non_contact"
# resp["roi_image"]           → cropped file URL
# resp["fullframe_image"]     → full-frame + overlay file URL
# resp["probability_contact"] → 0.0–1.0

裝好之後的驗收檢查

拿任何一張已知是 contact 的 RCM 截圖丟進 /api/v1/predict，看 response 的 features：

Featurecontact 預期區間non-contact 預期區間
lap_var21 – 2912 – 19
grad_mag40 – 577 – 38
edge_den0.01 – 0.080.00 – 0.01
mean51 – 6245 – 57
std24 – 3614 – 32

若實際數值嚴重偏離這些區間（例如 lap_var = 3 或 lap_var = 80），代表相機解析度或 framing 不對，不是 AOI 的 bug——請確認相機設為 1540 × 1050 且構圖正確。

儲存量估算 + 檔案回收

Monitor 每 aoi.interval_ms 呼叫一次（預設 200 ms = 5 Hz），每次 AOI 寫一行 JSONL log（約 400 B）；只有在 contact 時才寫 2 個 JPG（原圖 ~450 KB、裁切 ~20 KB）。粗估：

  • 每小時 log 行：18,000 × ~400 B ≈ ~7 MB（daily rotate，由 logging.backup_count 自動限制，預設保留 7 天）
  • 每小時 JPG：取決於實際 contact 比例。SOP 流程中 contact 是短暫瞬間，若平均每秒 ~1 次 contact 事件 → ~7,000 檔、~200 MB / 小時；idle 或正在找針尖高度時更少
  • 檔案回收 service 要清理的路徑（都可從 config/aoi_api.json 讀到）：
    • paths.contact_dir（預設 ./local_output/contact/*.jpg）——建議保留 24 小時
    • paths.log_dir 內已輪替的檔（aoi_api.log.YYYY-MM-DD）——當日 aoi_api.log 請勿刪除
    • paths.non_contact_dir v7.4 起不會有新檔產生（non_contact 不存檔）；資料夾保留以利未來擴充，回收 service 可以掃也可以略過

9. 特徵說明

五個特徵都計算於 ROI 的灰階影像、且經過 5×5 Gaussian blur。挑選標準：至少兩個特徵能單獨區分 contact / non-contact，當 probe card 類型改變時仍然 robust。

Feature衡量目標模型權重
lap_varLaplacian 變異數——銳利度 / 高頻訊號+2.23（主訊號）
grad_magSobel gradient magnitude 平均——整體邊緣強度+1.28（主訊號）
edge_denCanny edge pixel 比例+1.17（主訊號）
mean灰階平均強度+0.44
std灰階強度 std-dev−0.45（被 L2 regularize 到接近 0）
intercept−0.90

預測公式：sigmoid( weight · ((feature − mean) / std) + intercept )，在 0.5 處做判定。

10. 相機 / FOV 變更時的重新校正

若鏡頭、FOV、或 zoom 有明顯變動，特徵分布會偏移，需要重新校正。收集大約 10 張 contact 與 10 張 non-contact 的 labeled 影像，再執行校正 script（請找 API owner——這是一個小的訓練 script，會重寫 calibration.json）。

API 的程式與 endpoint 在校正前後不會改變。

11. 待確認事項（截至此版）

  1. roi_image 格式確定。 回傳的是本 API 內建 StaticFiles 提供的 URL path（GET /local_output/contact/<file>.jpg 或 /local_output/non-contact/<file>.jpg），monitor 自行加上 base URL 就能給前端 Web UI 顯示。
  2. category 欄位取消。 設計文件 monitor.json 裡的 aoi.category 不再需要——本 API 通用於所有 probe card。Monitor 可將該欄位留空，或（更保險）直接從上傳 payload 中移除。
  3. Log rotation + 檔案回收。 JPG 只在 contact 時儲存在 paths.contact_dir（v7.4 起 non_contact 不存檔）；JSON Lines log 儲存在 paths.log_dir，每日午夜自動輪替。檔案回收 service 請讀取 config/aoi_api.json 來知道所有需要掃描的路徑（詳見 §8 儲存量估算）。
  4. v7.4 行為變更：non_contact 不存檔。 response 的 roi_image / fullframe_image 在 non_contact 時回 null；log 也如實記錄 null。完整判定紀錄仍可從 log 的 features、probability_contact 欄位重建。

12. 疑難排解

現象可能原因修正方式
GET /api/v1/health 回傳 "calibrated": falsecalibration.json 缺失或格式有誤從本 package 還原該檔案；確認 config/aoi_api.json 的 paths.calibration_json 指到對的位置
已知是 contact 的影像都被判成 non_contact 且 p ≈ 0.0相機解析度或 framing 不對用 §8 的表格檢查 features 值，確認相機設為 1540 × 1050
POST 回 422 Unprocessable Entitymultipart 欄位名錯誤欄位名必須完全是 file
POST 回 500 且訊息含 計算出的 ROI 範圍無效上傳的圖太小，reference_roi 裁出來的 crop 是 0×0確認上傳的是完整 RCM 截圖，不是已經裁好的 ROI
POST 回 500 且訊息含 calibration missingcalibration.json 損壞或缺少 feature 資訊從 package 還原，重新啟動服務
啟動時 stderr 出現 WARN: config ... not found — using defaultsconfig 檔不存在或路徑錯確認從 package 根目錄啟動；或設定 AOI_API_CONFIG 環境變數
logs/aoi_api.log 一直沒有新內容paths.log_dir 無寫入權限，或 handler 初始化失敗檢查資料夾存在性與權限；重啟後觀察 stderr
Latency > 200 msAOI 本身約 25 ms，問題不在 AOI檢查網路以及 RCM 取圖時間
