   │       status="contact"     → ./local_output/contact/<timestamp>.jpg
   │       status="non_contact" → ./local_output/non-contact/<timestamp>.jpg
   │ 5. return JSON (status, roi_image URL, features, probability)
   ▼
monitor logs response, drives LED / Redis, debounces

One thing worth being explicit about

The file we save to local_output/contact/ or local_output/non-contact/ is the bytes we received — not a re-rendering. So:

- If monitor resizes the crop to 385 × 420 before uploading (my recommendation), the saved offline-review file will be 385 × 420.
- If monitor uploads an un-resized crop (any pixel size), the saved file will be at that larger size.

For offline review a human can see detail better in a larger crop than a resized one. Two options, pick whichever your colleague prefers:

1. Simple (what I set up): monitor resizes to 385 × 420, sends once. The saved offline file is 385 × 420. One upload per cycle, minimum bandwidth.
2. Nicer for review: monitor sends the un-resized crop without cv2.resize. AOI still works IF the camera is already at 1540 × 1050 (Option A from §5 of the README, so the crop is natively 385 × 420). If camera is at a different resolution, feature values will drift — don't use this option without recalibration.

So the cleanest setup is: colleague configures camera to 1540 × 1050, monitor crops with capture_roi = {x:385, y:473, w:385, h:420}, uploads the raw 385×420 crop (no resize step), and AOI saves that same 385×420 JPG into local_output/contact//non-contact/ for review.

Volume reminder

Polling at 5 Hz means roughly 18,000 JPGs/hour across both folders combined. The design doc's log-cleaner (§9) needs to sweep both ./local_output/contact/ and ./local_output/non-contact/ — otherwise disk fills up during a long run.
