AH9710 Contact Monitor — POC 設計

主鏡頭（RCM 影像）+ AOI 判定針尖是否接觸 Tape，以實體按鈕 / LED 及網頁同步操作與顯示。

1. 概要

依客戶 SOP 找 first pin 高度時，OP 會「下壓 → 接觸 → 後退規定距離 → 再下壓」反覆進行。因此啟動監控後，AOI 判定會一直在 CONTACT ⇄ NON_CONTACT 之間循環，直到再按一次按鈕停止監控。

服務 1

panel-io-service

操作面板 IO 服務。TCP Server，回報按鈕事件、依指令切換 LED 模式。POC 用 UART0 的兩支腳（GPIO14 按鈕 / GPIO15 LED），之後換成有 SoC 的 UART 面板時只要換驅動層。

服務 2

contact-monitor-service

監控邏輯服務，也是唯一的狀態擁有者。接收按鈕 / 網頁指令，從 RCM 取像、依 ROI 裁切、依設定頻率送 AOI-API 判定，再更新 LED 和 Redis 狀態。

UI

contact-monitor-web

網頁後端與前端。顯示藍綠色框範圍的即時影像、大字狀態（類似影片中的 OK）、Contact 時的 ROI 影像，以及開始 / 停止按鈕。只送指令、只讀狀態。另提供需登入的系統設定，修改後經確認才寫入並重啟相關服務。

三個服務共用同一套日誌模組：存放位置、檔案大小切割、命名格式、Log level 都可設定，每次啟動都會記錄 SERVICE_STARTED（見 第 9 節）。

3. 系統架構

實線藍色為 POC 新設計的 TCP 介面；虛線框為外部系統。即時影像不經過 contact-monitor-service，由網頁後端直接轉送 RCM 串流，避免監控服務被影像串流拖慢。

設計重點

  • 只有一個狀態擁有者。 實體按鈕和網頁按鈕最後都送到 contact-monitor-service，由它決定開始 / 停止，再同時更新 LED 和 Redis，兩邊自然同步。
  • panel-io-service 不記狀態。 它只回報「哪顆按鈕被怎麼按」，以及照指令亮燈。之後換成多按鈕、多燈號的 UART 面板時，只要改驅動層和按鈕對照表，監控邏輯不用動。
  • 網頁不寫狀態。 網頁只送指令並等狀態回報，從根本避免 hid-status-manager「網頁先切、又被 Redis 舊狀態切回」的問題（見 第 6 節）。

4. panel-io-service（操作面板 IO 服務）

職責

  • 按鈕去彈跳後判斷手勢（短按 / 長按），送出 BUTTON_PRESSED。
  • 依 SET_LED 指令執行燈號模式，閃爍節奏由本服務自行產生。
  • 心跳檢查：超過 5 秒沒收到 contact-monitor-service 的 ping，LED 自動關閉（fail-safe）。
  • 重新連線時先送 hello，contact-monitor-service 收到後重送目前的 LED 模式。

5. contact-monitor-service（監控邏輯服務）

監控流程

  1. 收到 START_MONITOR（網頁）或 BUTTON_PRESSED（轉成 TOGGLE_MONITOR）。
  2. 進入 STARTING：確認 RCM 有影像訊號、aoi-api 可連線。成功 → MONITORING；失敗 → ERROR。
  3. 每 aoi.interval_ms 一輪：向 RCM 取 snapshot 原圖 → 依 capture_roi（x, y, w, h）裁切 → 上傳 aoi-api。
  4. aoi-api 回傳 contact / non_contact 和 ROI 影像路徑；連續 debounce_count 次相同才改變 contact_state。
  5. 狀態改變時：送 SET_LED 給 panel-io-service、寫入 Redis 並 PUBLISH。每次 NON_CONTACT → CONTACT，contact_count 加 1。
  6. 持續 CONTACT ⇄ NON_CONTACT 循環，直到收到 STOP_MONITOR / 再按一次按鈕 → IDLE、LED_OFF。

狀態機

ERROR 狀態再按按鈕或網頁「開始」可重試。「逾時」指取像或 AOI 連續失敗超過 error_timeout_s。

aoi-api 介面（預期，修改中）

6. Redis 與狀態同步

要避免的現況問題（hid-status-manager）
網頁按下切換 RCM 後，畫面先切到 RCM；但 hid-status-manager 要等下層真的切換成功才改 Redis 的 status。期間網頁讀到 Redis 仍是 local.normal，畫面又被切回 Normal，直到下層成功後才再切回 RCM，造成閃動。
根本原因：網頁把「我想要的狀態」和「實際狀態」當成同一個值在顯示。

設計規則

  1. 指令和狀態分開。 網頁只往 contact:monitor:cmd（STREAM）寫指令；contact:monitor:state 只有 contact-monitor-service 會寫。
  2. 每個指令都有 cmd_id。 狀態裡記錄 last_cmd_id 和 last_cmd_result，網頁靠它確認「我送的指令處理完了沒」。
  3. 網頁顯示「處理中」，不先切換。 按下後按鈕變成「啟動中…」並停用，畫面狀態保持原樣，直到收到帶有同一個 cmd_id 的狀態更新；超過 3 秒沒回應就顯示錯誤，而不是自己切回去。
  4. 狀態有遞增的 seq。 網頁只接受比目前更新的狀態，晚到的舊訊息直接丟掉。
  5. 實體按鈕走同一條路。 按鈕 → panel-io-service → contact-monitor-service → 寫 state + PUBLISH，網頁收到後同步更新；LED 也由同一個狀態變更驅動。

8. 系統設定（網頁）

網頁提供系統設定頁，可以修改三個服務的設定。修改後要先確認，確認後才寫入設定檔並重啟受影響的服務。

登入與權限

  • 進入設定頁需要登入，帳號 admin，密碼依需求設定。密碼不以明文保存：web.json 只存 PBKDF2 雜湊，可在設定頁「帳號」區塊修改。
  • 登入後以 HttpOnly session cookie 維持登入狀態，閒置 30 分鐘自動登出（可設定）。
  • 連續 5 次密碼錯誤鎖定 5 分鐘；登入成功、失敗、登出都寫入日誌（LOGIN_SUCCESS / LOGIN_FAILED / LOGOUT）。
  • 監控畫面（開始 / 停止、即時影像、狀態）不需登入，OP 可直接使用；只有系統設定需要登入。
  • 密碼類欄位（RCM 密碼、登入密碼）不會回傳到瀏覽器，畫面只顯示 ••••••；留空表示不變更。

RCM 密碼加密保存

  • 設定檔不存明文，改存 "password_enc": "aesgcm:v1:<base64>"，使用 AES-256-GCM 加密（Python cryptography 套件，jeepKVM 沒有網路，和 aoi-api 一樣以離線 wheel 安裝）。
  • 金鑰檔 /opt/jtron/jeep/config/contact-monitor/secret.key：安裝時隨機產生 32 bytes，權限 0600，擁有者為執行服務的帳號 jtron；不放進備份、不隨設定檔複製。
  • 網頁儲存設定時加密寫入；contact-monitor 與 contact-monitor-web 啟動時讀金鑰解密，明文只存在記憶體，任何日誌都只顯示 ******。
  • 金鑰遺失或解密失敗時，服務記錄 CONFIG_INVALID 並停止啟動（套用設定時會觸發自動還原）；需在設定頁重新輸入 RCM 密碼。
  • 沒有網頁時也可在 jeepKVM 上用指令設定：contact-config set-secret rcm.password。
金鑰和設定檔放在同一台機器，所以加密的作用是：設定檔被複製、備份或外流時看不到密碼；能取得 jeepKVM root 權限的人仍可解密。

套用流程

  1. 編輯：欄位即時檢查格式與範圍（例如判定頻率 100–5000 ms），有修改的欄位會標示出來。
  2. 檢查變更：按「套用」後，後端再驗證一次，回傳「改了哪些欄位」和「要重啟哪些服務」。
  3. 確認：跳出確認視窗，列出原值 → 新值（密碼只顯示「已變更」）與要重啟的服務。若目前正在監控，提示「套用後監控會停止」。
  4. 寫入：先備份目前的設定檔到 config/backup/<時間>/，再以「寫暫存檔 → 改名」的方式寫入，避免寫到一半斷電造成檔案損壞；config_version 加 1，並記錄 CONFIG_CHANGED（操作者、修改欄位，密碼遮罩）。
  5. 重啟：依序 systemctl restart 受影響的服務，每個服務等它回報 SERVICE_STARTED 心跳（Redis contact:service:<name>，config_version 為新版本）或 systemd 為 active，最多等 15 秒。網頁服務自己需要重啟時排在最後，頁面顯示「網頁服務重新啟動中」並自動重新連線。
  6. 失敗還原：任一服務啟動失敗，自動還原備份的設定檔並再重啟一次，畫面顯示失敗原因，日誌記錄 CONFIG_ROLLBACK。

網頁重啟服務的權限

三個服務都以 jtron 帳號執行（不是 root）。網頁服務透過 sudoers 只能重啟這三個 unit，不能執行其他 root 指令。服務狀態用 systemctl is-active 查詢，不需要 sudo。

# /etc/sudoers.d/contact-monitor   （安裝時以 visudo -cf 檢查語法）
jtron ALL=(root) NOPASSWD: /usr/bin/systemctl restart --no-block contact-panel-io, \
                           /usr/bin/systemctl restart --no-block contact-monitor, \
                           /usr/bin/systemctl restart --no-block contact-monitor-web
  • 使用 --no-block：指令送出就返回，網頁再自己輪詢健康狀態，不會卡在 systemctl。
  • 網頁重啟自己時排在最後：先回應瀏覽器「網頁服務重新啟動中」，再送出重啟指令；瀏覽器每秒重試連線，連上後顯示套用結果。
  • 每次重啟都記錄 SERVICE_RESTART_REQUESTED（操作者、unit、原因）與 SERVICE_RESTART_RESULT。

9. 日誌機制

三個服務共用 jtron_log 日誌模組，設定格式相同，各自寫入自己的目錄。位置沿用 JEEP 的慣例 /media/disk/log/<服務>/（每台 jeepKVM 都有）。

與 log-cleaner 配合
jeepKVM 上的 log-cleaner 由 root crontab 每天 00:05 執行，會刪除 /media/disk/log/ 底下（含子目錄）修改時間超過 backup_days 天的檔案（設定在 /opt/jtron/jeep/config/log-cleaner/config.json），與檔名無關。因此：
  • 依天數清理交給 log-cleaner，本模組的 retention_days 預設 0（不另外依天數刪除）。
  • log-cleaner 只看天數、不看容量，所以本模組保留 max_size_mb × max_files 的容量上限，避免 DEBUG 等級在幾天內寫滿磁碟（預設每個服務最多 5 MB × 30 = 150 MB）。
  • 正在寫入的檔案修改時間一直是最新的，不會被 log-cleaner 刪掉。

可設定項目

設定預設值說明
levelINFODEBUG / INFO / WARNING / ERROR。DEBUG 會記錄每一次 AOI 判定結果與耗時。
dir/media/disk/log/{service}存放位置，{service} 會換成服務名稱；目錄不存在時自動建立。放在 /media/disk/log/ 底下才會被 log-cleaner 清理。
file_name{service}_{date}.log命名格式，可用 {service}、{date}（依 date_format）、{host}。
date_format%Y%m%d{date} 的格式；日期改變時自動開新檔。
max_size_mb5單檔上限，超過時切割成 …_20261106.1.log、.2.log，目前寫入的檔名不變。
max_files30每個服務最多保留幾個日誌檔，超過時刪除最舊的。
retention_days00 表示交給 log-cleaner；若需要比 log-cleaner 更短的保留期再設定天數。
consoletrue同時輸出到 console，systemd 會收進 journal（journalctl -u contact-monitor）。
format見下方每行格式，預設包含時間（到毫秒）、等級、服務名稱、事件代碼與內容。
