# 2.4 | Core Concepts: API, MCP, CLI, Skills, Artifacts, Projects

## Learning Objectives

- Use a single relationship diagram to clarify six frequently-appearing, easily-confused concepts;
- Be able to explain each concept in your own words to someone else, and give a corresponding real-world example;
- Understand the combinatorial relationships among these concepts, rather than memorizing definitions in isolation.

## Suggested Duration

30 minutes (concept overview + diagrams; recommended to use a whiteboard/slides)

## Prerequisites

- Have completed 1.4 (API), 1.6 (initial exposure to the Skills concept preview), and 2.3 (Projects). This lesson provides a systematic integration.

## Course Outline

### I. Why We're Dedicating a Lesson to These Six Terms

Learners have already encountered these terms scattered throughout earlier lessons, and it's easy to have "heard of them but not be able to clearly distinguish them." The goal of this lesson is not to introduce new knowledge, but to **reorganize what has already been learned into a clear map**, reducing cognitive load.

### II. Six Concepts, One-Sentence Definitions

| Concept | One-Sentence Definition | Which Lesson You Encountered It In |
|---|---|---|
| **API** | The interface through which applications communicate with each other — the underlying channel for all of Claude's capabilities | 1.4 |
| **CLI** | Command Line Interface — Claude Code is an agent tool that runs in the form of a CLI | 1.3 |
| **MCP** | Model Context Protocol — the standard protocol that lets Claude "plug into" external tools and data sources | Detailed in Chapter 5; this lesson builds an initial impression |
| **Skills** | Packaging an entire workflow into a "skill pack" that can be invoked with one click | Previewed in 1.6, detailed in Chapter 7 |
| **Artifacts** | Independently previewable outputs generated by Claude (web pages, charts, documents), displayed separately in a side panel | 1.2 |
| **Projects** | A long-term knowledge base + background configuration space within Claude Desktop | 2.3 |

### III. Relationship Diagram (Recommended to Present Visually; Expressed Here as a Hierarchical Structure)

```
API (the lowest-level channel, the foundation of all capabilities)
 └── CLI (a form that uses the API's capabilities: a command-line agent)
      ├── MCP (the protocol that lets the CLI/Agent connect to external tools and data sources)
      └── Skills (packages common workflows for reuse by the CLI/Desktop)

Desktop (graphical interface, also built on the API)
 ├── Projects (a container for long-term memory and knowledge bases)
 └── Artifacts (the display format for outputs generated within a single conversation)
```

**Key teaching points:**

- API is the "foundation," and CLI and Desktop are "two buildings" built on top of this foundation;
- MCP and Skills lean more toward "capability extensions on the CLI/Agent side";
- Projects and Artifacts lean more toward "the user experience on the Desktop side";
- But this is not an absolute separation — for example, the concept of Skills may also extend to broader scenarios. When explaining this, emphasize that "this is the most practical framework for understanding at the current stage, not a fixed, unchanging technical boundary."

### IV. Analogy-Based Memory Techniques (Classroom Interaction — Let Learners Create Their Own Analogies)

Provide example analogies to spark ideas, then have learners discuss their own analogies in groups:

- **API** is like a "water pipe" — the channel through which capabilities/data flow;
- **CLI** is like "the technician who brings the water pipe to do work for you";
- **MCP** is like "a full set of universal fittings given to the technician," letting them connect to different brands of faucets (external tools);
- **Skills** is like "the technician's professional toolkit" — when a specific job comes up, they pull out the right tool directly instead of learning it on the spot;
- **Artifacts** is like "the finished product the technician hands you after the job is done, ready for you to view directly";
- **Projects** is like "a dedicated filing cabinet you give the technician," containing all the background materials for this client/project.

### V. Comprehensive Quiz (Live Classroom Q&A)

A quick-answer format to check whether the concepts are clearly distinguished:

1. I want Claude to connect to my company's Feishu documents — which concept does that rely on? (MCP)
2. I want Claude to remember all of my brand's historical copywriting — which concept does that rely on? (Projects)
3. Claude generated a web page for me that I can preview directly — what is this display format called? (Artifacts)
4. I packaged the common workflow "generate a weekly report" into a one-click call — what is this? (Skills; the custom commands made in 1.6 are its early prototype)
5. What form does Claude Code itself run in? (CLI)

## Frequently Asked Questions

**Q: Are these concepts competing with each other — if I learn Skills, do I not need to learn MCP?**
A: No, they are not competitors — they are complementary. MCP solves the problem of "connecting to the external world," while Skills solves the problem of "capturing and reusing workflows." In real projects, both are often used together.

**Q: What if I can't remember all these concepts right now?**
A: You don't need to memorize the definitions by rote. This lesson's diagram will be placed in the course resource library, and Chapters 5 and 7 will go deeper into MCP and Skills with hands-on practice that reinforces these concepts again. It's normal not to remember them right away — they become clear naturally with use.
