# 2.1 | How to Create a Claude Code Working Folder

## Learning Objectives

- Understand the significance of the "Working Directory" for Claude Code;
- Master a reusable project folder structure standard;
- Be able to use `/add-dir` and similar methods to manage multi-directory access scope;
- Build a sense of "project boundaries": what Claude can see and what it shouldn't see.

## Suggested Duration

20 minutes

## Prerequisites

- Have completed Chapter 1 and can start the CLI normally.

## Course Outline

### I. What Is a Workspace, and Why Does It Matter

- When Claude Code starts, it uses the directory the terminal is currently in as the "workspace," and by default it can read and write files in this directory and its subdirectories;
- A workspace is roughly equivalent to giving Claude "a room it can move freely in" — by default, it cannot see or touch anything outside that room. This is both a capability boundary and a security boundary;
- This echoes the "permissions and security" thread from Section 1.1 of Chapter 1: workspace scope plus the operation confirmation mechanism together form Claude Code's first line of security defense.

### II. Recommended Project Folder Structure

Different types of projects will have different structures, but it's recommended to give learners a "universal starting point" to reduce decision-making overhead:

```
my-project/
  CLAUDE.md              # Project handbook (detailed in 2.2)
  .claude/
    commands/             # Custom commands (learned in 1.6)
    settings.json          # Project-level configuration (optional)
  docs/                   # Background materials, requirement documents
  assets/                  # Materials, images, reference files
  output/                  # Where Claude's outputs are stored
  .env                     # Keys and other sensitive configuration (must be added to .gitignore)
  .gitignore
```

**Design principle explanation:**

- `docs/` and `output/` are kept separate to avoid mixing "AI-generated content" with "the original background materials you provided," making later retrieval and review easier;
- `.claude/` is Claude Code's "dedicated configuration area." Keep all project customization content here to keep the project root directory clean;
- Regardless of project size, it's recommended to make a habit of creating `CLAUDE.md` right away (even if you only write a few lines to start).

### III. Hands-on: Create Your First Standardized Working Folder

1. Create a project folder in the terminal and navigate into it:

```bash
mkdir my-first-project && cd my-first-project
```

2. Create the basic directory structure:

```bash
mkdir -p docs assets output .claude/commands
touch .gitignore
```

3. Start Claude Code:

```bash
claude
```

4. Verify the workspace scope with a single sentence:

```
> What directory can you currently access? List all the files and folders in this directory
```

Observe the paths and folder structure it reports, and check whether they match your expectations.

### IV. Multi-Directory Management: `/add-dir`

- Some tasks require referencing data outside the workspace (for example, another shared asset library folder). You can use `/add-dir` to temporarily bring an additional directory into the accessible scope;
- Hands-on demonstration:

```
/add-dir ../shared-asset-library
```

- Remind learners: this is a **proactive authorization** action, and should only be done when there is a clear need and you trust the contents of the target directory. This is also a continuation of the security thread.

### V. Boundary-Awareness Discussion (Classroom Interaction)

Pose a question for learners to discuss: "If you started Claude Code at the root of your entire computer (for example, directly under `~` or `C:\`), what risks would that create?"

Guide the discussion toward this conclusion: workspace scope should be "just enough" — try to start Claude within a specific project folder rather than a broad, general directory. This both reduces the risk of accidental operations and helps Claude stay focused, reducing interference from unrelated files.

## Frequently Asked Questions

**Q: Does the folder structure have to strictly follow this template?**
A: No, it doesn't have to. This is a starting-point template meant to reduce decision-making overhead, and it can be adjusted based on the project type (writing project / code project / data analysis project). The core principle is to keep four categories of things separate: "handbook, raw materials, outputs, and sensitive configuration."

**Q: What happens if I forget to use `/add-dir`?**
A: When Claude needs to access a file outside the workspace, it will indicate that it cannot access it or will proactively ask whether the access scope should be expanded. It will not fail silently, nor will it bypass the boundary to access files on its own.
