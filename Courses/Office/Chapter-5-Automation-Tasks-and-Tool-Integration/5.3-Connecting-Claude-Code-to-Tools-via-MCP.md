# 5.3 | Connecting Claude Code to Tools via MCP

## Learning Objectives

- Understand the basic principles and design purpose of MCP (Model Context Protocol);
- Understand the relationship among MCP Client / MCP Server / Tool;
- Be able to independently evaluate "does the capability I need have a corresponding MCP Server, and is it worth connecting."

## Suggested Duration

25 minutes

## Prerequisites

- Have completed 5.2, with one successful hands-on experience already under your belt — this lesson fills in the principles.

## Course Outline

### I. Answering Last Lesson's Cliffhanger: How Does Claude "Learn" to Use a New Tool

- MCP (Model Context Protocol) is a standardized protocol that defines the common rules for "how to communicate" between an AI assistant (the MCP Client, such as Claude Code) and external tools/data sources (the MCP Server);
- Analogy: before MCP existed, every new tool integration required a custom-built "translation scheme." MCP is like unifying the electrical outlet standard — as long as a tool provider builds a "plug" to the MCP standard, any AI assistant that supports MCP can simply "plug in and use it," with no custom rework needed.

### II. Three Core Roles

| Role | Description |
|---|---|
| **MCP Client** | The party initiating the request — in the context of this course, typically Claude Code / Claude Desktop |
| **MCP Server** | The party providing a specific capability — can be an official or community-developed plugin that wraps access to a particular tool or data source |
| **Tool** | The specific functional unit an MCP Server exposes for the Client to call, such as "read a file," "query a database," or "send a message" |

- The "MCP Server" installed in 5.2 essentially added a batch of callable "Tools" for Claude;
- When handling a task, Claude autonomously determines — based on the currently available Tool list — whether it needs to call a particular tool to complete the task. This determination happens automatically and doesn't require you to manually specify "please use tool XX" (although you can explicitly specify this if you want).

### III. The Core Problems MCP Solves

- **Standardization**: no need to design a new integration approach for every new tool;
- **Ecosystem building**: any developer can build an MCP Server to the standard and share it, forming a reusable tool ecosystem (echoing Chapter 7's "50 Skills and open-source projects most worth installing");
- **Security boundaries**: each MCP Server's scope of capability is explicitly declared. Combined with the permission-confirmation mechanism (learned in Chapter 1), you can always see exactly which tool Claude called and what action it took.

### IV. How to Evaluate Whether an MCP Server Is Worth Connecting

Give learners a decision checklist:

- [ ] Is this a capability I need repeatedly, and is doing it manually cumbersome?
- [ ] Does this MCP Server come from a trustworthy source (official, a well-known open-source project, actively maintained)?
- [ ] Does connecting it require granting an overly broad scope of permissions, and does it comply with the principle of least privilege (echoing what was learned in 4.7)?
- [ ] Is there an alternative (such as writing your own script, as learned in 5.1), and is MCP's advantage over writing your own script clear?

### V. Hands-On: Exploratory Integration of a New Tool-Type MCP Server

Choose a scenario close to learners' actual needs (such as database querying, web scraping, project management tools, or any similar category — the instructor should select the example based on current ecosystem availability), and walk learners through the full process of "evaluate → install → verify → actually use," deepening their practical feel for the underlying principles.

## Frequently Asked Questions

**Q: Is it better to install as many MCP Servers as possible?**
A: No — every Server you connect represents a larger scope of capability and a wider permission exposure. It's recommended to follow the principle of "connect only as needed," and to periodically review and remove Servers you're no longer using, reducing unnecessary security exposure.

**Q: Is MCP in competition with the "write your own script" approach from 5.1?**
A: They're complementary. A script you write yourself is well suited to scenarios that are "highly customized in logic and used only by you." An MCP Server is well suited to scenarios with "a high degree of standardization where the community already has a mature solution" — for example, connecting to a well-known third-party service, where using a ready-made MCP Server is usually more effort-efficient and reliable than building it from scratch yourself.
