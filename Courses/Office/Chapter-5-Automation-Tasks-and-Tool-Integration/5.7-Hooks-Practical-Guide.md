## Course Outline

### I. Why Higher Automation Requires More Hooks

- Review the arc of this chapter: 5.1 taught you to write scripts, 5.2–5.5 taught you to connect to a wider range of external capabilities, and 5.6 taught you to have scripts run automatically — the degree of automation and the scope of permissions in the workflow have kept expanding;
- The problem that follows: the higher the degree of automation, the greater the impact if "something goes wrong at some step." If it's entirely a "black-box execution," it's hard to catch or intercept a problem right away;
- The value of Hooks: inserting "automatic checkpoints" at key points in the workflow, achieving "automation without losing control."

### II. The Basic Principle of Hooks

- Hooks are an event-driven mechanism: when a particular event occurs (such as "before every file write" or "after every task completes"), a piece of logic you've pre-configured is automatically triggered;
- This triggered logic can be: an additional check, logging, sending a notification, or even blocking an operation from proceeding;
- Analogy: Hooks are like "sensors + safety gates" installed on an automated production line — the line itself runs automatically as usual, but sensors at key stations check in real time, and automatically shut the gate if something abnormal is detected.

### III. Common Hook Trigger Points (examples — refer to current version documentation for exact event types)

| Trigger Point | Typical Use |
|---|---|
| Before command execution | Double-confirm or directly block high-risk commands |
| Before a file write/modification | Check whether a file that shouldn't be touched (such as a config file or key file) is being modified |
| After task completion | Automatically log the result, send a completion notification |
| At session start | Automatically load specific background information or run environment checks |

### IV. Hands-On: Configuring a "High-Risk Command Interception" Hook

Scenario: you're worried that an automation script or Claude, running in automatic mode, might accidentally execute a dangerous delete-type command. Configure a Hook to intercept and confirm before this type of command executes.

```
> Please help me configure a Hook: before executing any command containing "rm -rf" or similar
> dangerous delete commands, first print a clearly visible warning log, and require an additional
> manual confirmation before proceeding
```

Walk through together with learners:

1. Review the content and location of the Hook configuration file Claude generated;
2. Understand the basic structure of the configuration (the triggering event type + matching condition + the action executed upon trigger);
3. Deliberately trigger an operation that meets the condition, to verify the Hook intercepts/warns as expected.

### V. Hands-On: Configuring a "Task Completion Notification" Hook

Scenario: combined with the scheduled automation from 5.6, you want to receive a notification when the script finishes running, instead of having to proactively check the logs.

```
> Please help me configure a Hook: after the automation script's task completes, write a summary
> of the execution result to a log file, and indicate in the summary whether it succeeded or failed
```

## Frequently Asked Questions

**Q: Does every automated task need Hooks configured?**
A: Not necessarily — the higher the risk, the higher the degree of automation, and the longer the unsupervised runtime, the more a task should have corresponding Hooks configured as a safety net. Simple, low-risk tasks that you'll frequently be present to check on can go without Hooks for now.

**Q: If a Hook is misconfigured, could it end up intercepting normal tasks too?**
A: Yes, that's possible. After configuring a Hook, always test it against several normal scenarios as well as several scenarios that should be intercepted, to confirm the matching condition is precise and doesn't accidentally affect normal operations.
