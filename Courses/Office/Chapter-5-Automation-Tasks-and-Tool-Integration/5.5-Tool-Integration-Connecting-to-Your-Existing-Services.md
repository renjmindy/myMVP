# 5.5 | Tool Integration: Connecting Claude Code to Your Existing Services

## Learning Objectives

- Understand how to connect your own existing services/systems to Claude Code when no ready-made MCP Server exists;
- Master the method of using API documentation to have Claude quickly build a custom connection for you;
- Complete one real hands-on exercise connecting to a service you already have.

## Suggested Duration

30 minutes (hands-on walkthrough)

## Prerequisites

- Have completed 5.1–5.4, and understand both the scripting approach and the MCP approach to connections.

## Course Outline

### I. What Problem This Lesson Solves

- 5.2–5.4 covered "using ready-made MCP Servers," but in reality, you might have your own company/team's internal systems (an internal admin backend, a self-built small tool, a private API) for which no ready-made MCP Server exists;
- This lesson explains how, in this situation, to have Claude Code help you bring an "existing service" into your workflow, without having to wait for a ready-made solution to appear in the community.

### II. Two Typical Paths

**Path One: Write a dedicated MCP Server for your own service**

- Suitable scenario: this connection needs to be used repeatedly and reliably, and you want it to be callable in a standardized way, just like the ready-made Servers in 5.2–5.4;
- General approach: wrap your existing service's API interface according to the MCP protocol specification into a Server, after which you can use it just like any third-party MCP Server.

**Path Two: Directly wrap the API call in a script (more lightweight)**

- Suitable scenario: the connection need is relatively simple, one-off or low-frequency, and doesn't warrant the complexity of a "standardized Server";
- Directly reuse the scripting method learned in 5.1, having Claude write a script that calls your service's API.

> Instructor note: neither path is absolutely superior — the core criterion is "will this connection be reused frequently in the future, and does it need to be managed in a standardized way." Simply emphasize: "important and high-frequency → Path One; lightweight and low-frequency → Path Two."

### III. Hands-On: Quick Connection Example via Path Two (better suited to class time constraints)

Using "connecting to an existing internal data-query API" as an example:

**Step 1: Provide the API documentation/interface description**

Provide your existing service's API documentation (endpoint address, authentication method, request/response format) to Claude — this can be a document file or a direct description.

**Step 2: Ask Claude to write the calling script**

```
> Based on the interface description in @api-docs.md, please help me write a script that:
> 1. Authenticates using the API Key I provide
> 2. Calls [specific endpoint] to fetch data
> 3. Formats the returned results into an easy-to-read table and prints it out
```

**Step 3: Handle authentication information securely**

- Emphasize: authentication information such as API Keys must be passed in via environment variables (echoing the key-management principles learned in 1.4) — Claude must not hardcode the key into the script file;

```
> Please make sure the script reads the API Key from an environment variable, and does not
> write the key directly into the code
```

**Step 4: Test and validate**

First validate that the script's logic is correct using credentials from a test/sandbox environment, then switch to the production environment for actual use.

### IV. Hands-On: Brief Walkthrough of Path One (advanced — not a deep-dive focus)

Briefly explain the general process of MCP Server development (define the list of tool capabilities → implement the processing logic for each tool → expose the interface per the protocol specification → test and register locally), and note that this is an advanced topic. For learners with an ongoing, standardized connection need, this can be explored after class by having Claude Code guide them through building it step by step, as a direction for deeper learning.

### V. Security Reminders for Connecting Your Own Services

- Connecting a self-built service means Claude may gain read/write access to your business data — always validate in a test environment first, and only connect to production after confirming everything is correct;
- Clearly identify which operations are "read-only queries" and which are "write operations that modify data," maintaining a higher degree of caution for write operations, and where necessary, combine this with the Hooks mechanism from 5.7 to add an extra layer of confirmation/restriction.

## Frequently Asked Questions

**Q: What if I have no API documentation at all?**
A: If the service was developed by you or your team, you can ask a developer colleague to help put together an interface description. If documentation truly doesn't exist, you can also have Claude help infer the interface logic by reverse-engineering the existing code — but this approach carries higher risk, so be sure to strengthen testing and validation.

**Q: Are there security risks in connecting to my own services?**
A: The core risk points are improper credential management and an overly broad permission scope. As long as you follow the three principles of "manage keys via environment variables + least privilege + test environment first," the risk is manageable.
