# 5.8 | Hands-On: Automated Daily Report System

## Learning Objectives

- Assemble all the techniques learned in 5.1–5.7 (scripting, MCP, custom service connections, scheduled tasks, Hooks) into a complete hands-on case study;
- Independently build an automated system that "generates and sends a daily report every day";
- Honestly understand the capability limits of a local-machine solution, and know where to go next to close the gap (leading into 6.5 of Chapter 6).

## Suggested Duration

35 minutes (hands-on walkthrough)

## Prerequisites

- Have completed 5.1–5.7. This lesson introduces no new concepts — it's a comprehensive application of previously learned techniques.

## Course Outline

### I. Why Use a "Daily Report System" as the Capstone Case

- 5.1–5.7 each covered one independent technique — scripting, MCP connections, custom service connections, scheduled tasks, and Hooks — but in real work, these are rarely used in isolation; a genuine automated system is usually a combination of these techniques;
- A daily report system is an example almost everyone can map onto their own work scenario: periodically (daily/weekly) collecting information from a number of data sources, compiling it into a structured summary, and automatically sending it to the people who need it.

### II. System Design: Breaking It Down into Assemblable Modules

Walk learners through sketching a module diagram for the entire system, and map each module back to the lessons they've learned:

```
① Data collection (maps to 5.2–5.5: MCP / custom service connections)
    — Pull the day's key information from sources such as task management tools, code repositories, sales data, etc.
② Compilation and generation (maps to 5.1: writing a script from natural language)
    — Use a script to compile the collected raw data into structured daily-report content
③ Scheduled triggering (maps to 5.6: Cron scheduled tasks)
    — Set the entire process to run automatically at a fixed time each day
④ Safety and control (maps to 5.7: Hooks)
    — Add a check before the sending step, to avoid mistakenly sending out abnormal data
⑤ Sending/delivery (new: email or Cowork collaboration tools, echoing 4.7/4.10 of Chapter 4)
    — Send the generated daily report to an email inbox, or write it into a collaboration tool such as Feishu/Notion
```

### III. Hands-On: Building Your Daily Report System

**Step 1: Determine the data source (reusing 5.2–5.5)**

```
> I want to build an automated daily report system. The data source is [your actual data source,
> e.g., GitHub commit history / a task management tool / a sales spreadsheet]. Please help me
> confirm whether this data source already has a corresponding MCP Server I can connect to directly;
> if not, help me write a connection script using the method learned in 5.5
```

**Step 2: Compile and generate the report content (reusing 5.1)**

```
> Please help me write a script that compiles the raw data collected in the previous step into a
> daily report, formatted as: today's completed items, items to follow up on, and anomalies that
> need attention. Tone: concise, bullet-point style, no more than 300 words
```

**Step 3: Add a safety check (reusing 5.7)**

```
> Please help me configure a Hook: before the daily report is officially sent, check whether the
> content is empty or clearly abnormal (such as missing content due to a failed data fetch). If
> an anomaly is detected, pause the send and give me a warning log, instead of sending out a
> blank or erroneous report
```

**Step 4: Set up daily scheduled execution (reusing 5.6)**

```
> Please help me configure this daily-report generation process to run automatically at 9 AM every
> day, and make sure logging is complete so I can troubleshoot afterward if needed
```

**Step 5: Connect the delivery channel (new, echoing Chapter 4)**

```
> Please help me send the generated daily report by email to [recipient], or write it into the
> Feishu/Notion document I connected in Chapter 4
```

### IV. Honest Boundaries: What This System Can and Cannot Do Right Now

- At this point, you have a system that "automatically generates and sends a daily report on schedule every day" — but recall what was covered in 5.6: **this system depends on your computer being powered on**. If the computer is off or asleep, the scheduled task won't trigger;
- In other words, this system hasn't yet achieved "close the computer and the AI keeps working for you" — that final step requires deploying it to the cloud, which is exactly what Section 6.5 of Chapter 6, "Moving to the Cloud: Using Vercel Cron to Run Scripts 24/7," will address;
- What this lesson delivers is a local-machine version that "runs through completely once, with correct verified logic." 6.5 will teach you to migrate this same logic to the cloud, achieving truly device-independent automatic execution.

### V. Ways to Further Extend This Case

- Multiple data sources can be layered together (e.g., pulling both task progress and sales data at the same time);
- You can generate different levels of detail for different recipients (a team version vs. a management summary version);
- You can package this entire workflow, using the method learned in Section 7.3 of Chapter 7, into a formal Skill that can be invoked with a single call in the future.

## Frequently Asked Questions

**Q: I don't have a ready-made data source (e.g., no team task management tool) — can I still practice this case?**
A: Yes — you can substitute any data you have on hand, such as "organize my own calendar schedule every day" or "compile updates from a certain website every day." The core is practicing the assembly method of "collect → compile → schedule → safety-check → send." The specific data source isn't the point.

**Q: What's the difference between this lesson and 5.1–5.7 — do I need to learn new things again?**
A: No new concepts are needed. This lesson deliberately introduces no new techniques — the goal is for you to personally assemble the five building blocks you've already learned into a real, usable system, testing whether you've truly mastered how to combine these techniques.

## Homework

Build your own complete automated daily report system (even with a very simple data source), actually run it for at least one full cycle, record the execution logs, and consider what adjustments the current script would need if you were to deploy it to the cloud (6.5).
