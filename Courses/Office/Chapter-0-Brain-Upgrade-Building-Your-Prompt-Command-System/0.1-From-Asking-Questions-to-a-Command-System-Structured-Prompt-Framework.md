# 0.1 | From "Asking Questions" to a "Command System": A Structured Prompt Framework

## Learning Objectives

- Understand the actual difference in output quality between two communication styles: "casual questions" and "structured commands";
- Master a reusable four-element Prompt framework: Goal, Context, Format Requirements, Constraints;
- Be able to rewrite a vague task into a clearly structured instruction that AI can execute consistently.

## Suggested Duration

30 minutes

## Prerequisites

None — this lesson is the starting point of the entire course.

## Course Outline

### I. Why "Asking Questions" Produces Inconsistent Results

- Most people use AI like a "question-and-answer" search engine — asking whatever comes to mind, getting a result, and whether it's satisfying is left entirely to luck;
- The root cause isn't that the AI isn't capable enough — it's that **the task itself has not been clearly defined**: the AI doesn't know what your goal is, what the background information is, what format you want, or what boundaries it can't cross, so it can only guess;
- Analogy: if you ask a new colleague to help you and only say "help me put together a report," the result is unlikely to be what you wanted. If you clearly state "who this report is for, what conclusions to highlight, how long it should be, what tone to use," the result will be far more consistent. The same logic applies to AI.

### II. The Four-Element Structured Prompt Framework

Give learners a directly applicable framework that covers the vast majority of tasks:

```
1. Goal        —— What should this task accomplish? What defines "done"?
2. Context     —— What background information does the AI need to get this right?
3. Format      —— What form should the output take? (length, structure, tone)
4. Constraints —— What can't be done, and what boundaries must be respected?
```

**Comparison Example (for classroom demonstration):**

| Casual Question | Structured Prompt |
|---|---|
| "Help me write an email chasing a client for payment" | "Goal: Write a payment-reminder email, professional in tone but still polite, aiming to get the client to complete payment within 3 days. Context: The client is a long-term partner; this is the second reminder, and the first reminder received no response. Format: Keep it under 150 words, and include a clear payment deadline. Constraints: Do not use threatening language, and preserve the possibility of continued cooperation." |

Have learners read both versions aloud together so they can directly feel the difference that comes from having a clear goal, sufficient context, a specific format, and well-defined boundaries.

### III. Hands-on: Rewriting Practice

**Step 1: Write down one of your own real tasks, described casually in a single sentence**

For example: "Help me summarize this meeting record."

**Step 2: Fill in the four elements one by one, using the framework**

```
Goal: ___________
Context: ___________
Format: ___________
Constraints: ___________
```

**Step 3: Ask Claude using both versions separately, and compare the results**

Walk learners through actually sending both the "casual version" and the "structured version" to Claude, and comparing the two outputs side by side for quality, usability, and whether a second round of revision is needed.

### IV. The Four Elements Are Not a Rigid Template

- Emphasize: the four elements form a "checklist," not a form that must be filled in word for word — once you're skilled at this, you'll naturally cover all four points within a single sentence, without literally writing out separate lines like "Goal: xxx";
- For simple tasks, unnecessary elements can be omitted (for example, if the other party already knows the "context," it can be skipped). The core is building the habit of "thinking through these four points before issuing a task."

### V. Class Discussion: Why "Consistency" Matters More Than "Brilliance"

Pose the question: "Have you ever noticed AI writing something exceptionally well one time and mediocrely another, even when asking it to write the same kind of thing?" Guide learners to the conclusion: this inconsistency is usually not a problem with the AI itself, but with the amount of information given in the instructions varying each time — the core value of a structured framework is making high-quality output **repeatable**, rather than relying on luck to land a good result once.

## Frequently Asked Questions

**Q: Won't it be a hassle to write things out in this much detail every time?**
A: It will feel like extra work during the early practice stage, but once you're skilled at it, you'll find that the time spent clearly writing out the four elements is usually far less than the time spent going back and forth revising an unsatisfying result — over the long run, it's a net time saver.

**Q: Do I need to use this framework even for very simple tasks?**
A: No — simple tasks with clear boundaries (like "translate this sentence into English") don't need to be forced into the framework. The framework really earns its value on tasks that have some complexity and are prone to ambiguity.

## Homework

Choose 3 real tasks you've recently wanted AI to handle. For each one, write both a "casual version" and a "structured version" of the prompt, actually test them, and record the difference in output quality between the two.
