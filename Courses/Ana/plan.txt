Context

The user (screenshot prompt) wants a data-scientist-style pipeline: parse an Apple Health export.xml, load it into BigQuery, run SQL analysis on energy/exercise trends, and produce data-driven insights + recommendations, with all code stored in /home/cjen/myMVP/Courses/Ana.

Two environment gaps were found and resolved with the user:
- Data scope: export.xml is already present locally (Drive download step is moot) but contains only 1,000 HKQuantityTypeIdentifierHeartRate records spanning Jan 16–27, 2020 — no ActiveEnergyBurned, Workout, or ActivitySummary records. Decision: use this file as-is. The parser will be written generically (handles any record type), but the actual analysis/report will be scoped to what's really in the data (heart rate trends), with the limitation stated explicitly rather than glossed over.
- BigQuery: not configured (no gcloud, no google-cloud-bigquery, no credentials). Decision: set up real BigQuery. This requires one manual step from the user (auth), called out below.

The GitHub repo referenced in the prompt (yudong-94/Apple-Watch-Data-Exploration) exists publicly and is optional inspiration only — no action needed unless the parser design benefits from a peek at it.

Prerequisite (user action, before step 3)

BigQuery access must be established before loading data:
1. Install: pip install google-cloud-bigquery
2. Auth: run gcloud auth application-default login in the terminal (suggest the user do this via ! gcloud auth application-default login), or supply a service-account JSON key path.
3. Provide a GCP project ID with the BigQuery API enabled (billing must be active on the project).

I'll pause and ask for these once the parsing step is done, rather than blocking earlier work on it.

Files to create (all in /home/cjen/myMVP/Courses/Ana)

- parse_health_export.py — parses export.xml with lxml.etree.iterparse (streaming, memory-safe) into pandas DataFrames, one per top-level element type actually present (Record, and Workout/ActivitySummary if present later). Extracts: type, sourceName, sourceVersion, unit, creationDate, startDate, endDate, value, plus flattened MetadataEntry key/values where present. Writes Parquet files (records_heartrate.parquet, etc.) as the load-ready output — one file per HealthKit type.
- load_to_bigquery.py — uses google-cloud-bigquery client to create dataset apple_health (if absent) and one table per parquet file via load_table_from_dataframe with an explicit schema (typed timestamps, not autodetected strings). Takes --project arg.
- analysis_queries.sql — the actual SQL run in BigQuery: time-series aggregation (daily/hourly avg & resting heart rate proxy via HKMetadataKeyHeartRateMotionContext), gap/anomaly detection (missing days, outlier values via stddev bounds), and consistency-over-time metrics. Written generically so ActiveEnergyBurned/Workout queries can be dropped in unchanged if a fuller export is loaded later.
- run_analysis.py — orchestrator: runs each query via the BigQuery client, pulls results back into pandas, and renders a couple of matplotlib charts (saved as PNGs) for the trend/anomaly sections.
- report.md — final write-up structured per the original requirements: explicit assumptions (data scope limitation, timezone handling, motion-context heuristic), a Findings section with only data-supported observations, a separate Recommendations section clearly labeled as general health/fitness guidance (not data-derived), and a short Data Limitations callout.

Step-by-step execution

1. Write parse_health_export.py; run it locally to produce the parquet file(s); sanity-check row counts/dtypes.
2. Ask the user for the BigQuery prerequisites (project ID + confirmation auth is done) before touching the cloud.
3. Write load_to_bigquery.py; run it to create the dataset/table and load the parquet data; verify row count in BigQuery matches the parquet row count.
4. Write analysis_queries.sql and run_analysis.py; run it against BigQuery; inspect returned DataFrames/charts for sanity (e.g., date range matches Jan 16–27 2020, no null timestamps).
5. Write report.md summarizing findings and recommendations per the separation requirement above.
6. Final pass: confirm all code files are documented (module docstring + inline comments only where non-obvious, per house style) and located in the target directory.
